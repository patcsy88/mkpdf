### ARCH-F-01 (medium): ADR-0003 vs D-08

- Evidence: `docs/adr/0003-opaque-handle-c-abi.md:9,21` (handles are opaque pointers; double free and use after free "are undefined behaviour", with "debug-time handle validation" left as "an open option for GATE-1"). `docs/requirements.md` D-08 (owner decision: build generation-checked handles, amends ADR-0003, changes the ABI, needs a new ADR, comes before FFI-001). `docs/roadmap.md` FFI-003. `crates/mkpdf-ffi/src/lib.rs:153-182` (handles are raw `Box` pointers). `docs/adr/README.md` before this review listed no ADR for it.
- Problem: a Proposed ADR states the opposite of an owner decision, and the ADR that must carry the decision does not exist. D-08 is not a small change. A pointer cannot be checked for staleness without reading it, and reading freed memory is itself undefined behaviour (as `gate-1-security.md` SEC-F-04 also says). A real check needs a handle table with generation counters. That moves the handle type from a pointer to an integer or token, adds global state with a lock or atomics to the FFI crate, and changes every signature and the header. `mkpdf-core` stays untouched, since the table belongs in the FFI crate.
- Open design points the new ADR must settle: handle representation (a `uint64_t` token, or a pointer-typed token that is never dereferenced), table growth and its limit, locking and its effect on the "distinct handles may run concurrently" rule (`rules/interoperability.md` item 6), whether the thread contract for one handle can now be checked (a busy flag), what `*_free` reports for a stale handle (it returns `void` today), how the error text API interacts, and the cost for the Go, Python, Node, .NET and Java wrappers, which should treat the token as an opaque 64-bit value.
- Disposition: write the ADR (architect) and supersede or amend ADR-0003 in the same change. The owner accepts it. Do this before FFI-001 and re-read ADR-0012 against it. ADR-0012 is written so that the buffer is a handle of the same kind and gets the same checking. Condition AC-2.

### ARCH-F-03 (medium): ABI version rule for 0.x

- Evidence: `docs/adr/0004-abi-and-api-versioning.md:7-10` (change or removal raises the major; bindings refuse a different major; "until v1.0.0 the ABI is 0.x and may change"), `rules/interoperability.md` item 7 (same, "changing or removing anything raises the major version"), `crates/mkpdf-ffi/src/lib.rs:19-21` (major 0, minor 1), `docs/api/c-abi.md:3`. `docs/requirements.md` D-08: the ABI changes at 0.x.
- Problem: if a breaking change raises the major, the first break (FFI-003) makes the ABI 1.0, which contradicts "frozen at v1.0.0". If a breaking change at 0.x raises only the minor, bindings that check only the major accept an incompatible library. The text supports both readings. The next change forces the choice, and the check is the only defence a binding has against loading a mismatched library.
- Proposed rule for the owner: while the major is 0, bindings accept only an exact match of major and minor, and any change that is not a pure addition raises the minor. From 1.0, the rules in `interoperability.md` apply as written. `rules/interoperability.md` would then need an amendment (the architect proposes it, the owner approves it, since it is a rule file).
- Disposition: decide in ADR-0004 (Proposed) before FFI-003. Also add the SDK and ABI compatibility table that ADR-0004 (Consequences) promises and that `docs/api/c-abi.md` does not have. Condition AC-3. I did not edit ADR-0004 in this pass.

### ARCH-F-04 (medium): panic strategy

- Evidence: `Cargo.toml:34-38` (no `panic` key), `crates/mkpdf-ffi/src/lib.rs:96-111`, `docs/requirements.md` OQ-12. Reproduced: `catch_unwind` catches under `-C panic=unwind` (exit 0) and the process aborts under `-C panic=abort` (exit 134).
- Problem and options: see ADR-0011. The guard silently stops working under `abort`, and nothing detects that.
- Disposition: ADR-0011 (Proposed) recommends `unwind`, pinned in both profiles, a `compile_error!` under `panic = "abort"`, a CI check, a panic test through an exported function, and a rule for handle state after a caught panic. Needs Security Engineer review and the owner's decision. Condition AC-1.

### ARCH-F-05 (medium): header generation

- Evidence: `include/mkpdf.h:15-16` defines `MKPDF_ABI_MAJOR` and `MKPDF_ABI_MINOR`. The Rust constants are `ABI_MAJOR` and `ABI_MINOR` (`lib.rs:19,21`). cbindgen output for the same crate contains `#define ABI_MAJOR 0` and `#define ABI_MINOR 1`, and uses `struct MkpdfDocument *` in signatures where the committed header uses the typedef name. The status code macros match. `rules/interoperability.md` item 8 says the header "is generated by cbindgen and checked in CI against the committed copy". `docs/api/c-abi.md:64-66` says CI must generate it (FFI-001).
- Problem: with no cbindgen configuration in the repository, a CI diff would fail on day one, or the maintainers would adopt the generated names and change the public macro names. `cbindgen` is available locally (0.29.4), so the work is possible now. The committed header is correct today: I compiled, linked and ran a C program against it. The header also holds the ABI contract comments, which cbindgen takes from Rust doc comments, so that documentation would move into `lib.rs`.
- Disposition: devops and interop. Add `cbindgen.toml` (rename rules so that macro names stay `MKPDF_*`), generate, diff in CI, and add the C compile-and-link test as a CI step. Until then keep the hand-written header and say so (the ABI doc already does). Condition AC-4. The buffer functions sketched in ADR-0012 must be checked against cbindgen output.

### ARCH-F-07 (medium): limits

- Evidence: `rules/architecture.md` item 6 (every input-driven allocation, recursion and loop needs a documented limit, "covered by tests"). `docs/requirements.md` ("Architectural decisions identified") lists resource limits as needing an ADR, and none exists. `grep MAX_PAGES crates/` finds the definition (`model.rs:8`), the check (`model.rs:86`) and the re-export. ### ARCH-F-08 (medium): determinism default

### ARCH-F-14 (low): `_` arm in error mapping

- Evidence: `docs/adr/0008-error-model.md:8` (unknown future kinds map to `MKPDF_ERR_INVALID_ARGUMENT`), `crates/mkpdf-ffi/src/lib.rs:52-55` (`_ => MKPDF_ERR_INVALID_ARGUMENT`).
- Analysis: across crates a wildcard is required for a `#[non_exhaustive]` enum, so this is correct. The consequence is that adding an `ErrorKind` compiles silently and degrades to `INVALID_ARGUMENT`, and the ADR says "needs a deliberate ABI decision" without a mechanism.
